# `@lexical/y`: Decision Register

The decisions that shape `@lexical/y` and the core APIs it relies on, with the
reason for each. Read it before changing the package or reviewing a pull
request to it.

A `DECIDED` row is not re-opened without new evidence (a repro, a
measurement, a use case it did not consider). When a pull request makes a new
consequential decision, or changes one recorded here, it adds or updates the
row in the same pull request. Rows are never deleted: a replaced decision
says what replaced it.

## Status legend

| Status           | Meaning                                                                                        |
| ---------------- | ---------------------------------------------------------------------------------------------- |
| `DECIDED`        | Ratified. Do not re-open without new evidence.                                                 |
| `ACCEPTED LIMIT` | A known behaviour that was weighed and accepted, usually rare and losing no text. Documented in [Limits][limits]. |
| `OPEN`           | Undecided: a trade-off or design question waiting on research or a maintainer's call.          |

Dates are when the decision was made (2026). Links go to the pull requests,
issues and docs that carry it.

| D01 | **Zero breaking changes in released packages.** Changes to public APIs, behaviour and serialized formats are additive or opt-in. `@lexical/y` is a new, opt-in package; a behaviour change for existing users goes to a separate deprecation track. | D09 | **Layout version gate.** The root is `lexical-y`, not a `@lexical/yjs` root; it records `lexical-y:<n>` per layout it needs, and the record only grows. | D102 | **Layout migrations: frozen chained steps run by the authority, and a generation fence.** The core reads and writes layouts from `MIN_LAYOUT` to `LAYOUT_VERSION`; a root below the floor binds read only (`UNSUPPORTED_LAYOUT_WARNING`, `'older'`). A frozen step per layout (`@lexical/y/migrate/<n>to<n+1>`, never imported by the core) migrates a root in place, in one transaction under a hashed client id, recording the layout and an epoch (`lexical-y-epoch`): a versioned migration epoch (`v`, `kind`, the layout after it, the transition's first item, an opaque namespaced step id, its revision, and an optional app `schema`) that readers accept with fields they do not know, so later migration families (an app's schema steps) record their transitions in it. A step's `(id, revision, v)` names fixed output bytes for fixed input bytes: each step's default export stays revision 1, an output-changing correction is a new, separately named revision an app selects, golden fixtures are pinned per revision, and the runner's default target stays `MIN_LAYOUT`, which rises only when a release raises the floor (D110). One manifest (`src/migrate/manifest.json`) lists the published steps; the package's exports, the runner's lazy loader table (`loadYMigrationSteps`'s default) and the server's static table (`prepareYRoom`'s default) are generated from it, and the core imports none of them: adding a step is its file, its Flow declaration and one manifest line, then `pnpm run update-packages`. A root may declare features its content needs (`lexical-y-require:<feature> = true`, grow-only, opaque ids): a reader missing one, or finding one that is not well formed, opens the root read only, keeps it and never rewrites it; other unknown `lexical-y-*` attributes are kept and ignored. The authority that stores a document migrates it on load, behind a barrier and a compare-and-set, after checking the result on a copy; one result is ever published. Client-side migration is deferred from v1: it can be added later as an additive change on request, with its own option or entry, loaders, and an explicit single-writer assertion. A generation (an incarnation plus, per served root, the identity of the transition that last migrated it; a versioned, frozen algorithm, `g1:`, opaque to clients; a malformed epoch never yields one) is kept beside each state and each client replica; a replica of another or unknown generation that holds material is never synced: it hands its material to a per-document quarantine (versioned records, hashed with SHA-256 over a canonical payload that includes the source generation) and keeps it until a durable acknowledgement scoped to the room, replica, source generation, record and hash, then rebinds; the authority will replay the copy's own changes as a checked edit (by Yjs identity; a format or attribute change only where its base value is known and still current; a follow-up) and shows the rest in a recovery view. A pristine room admits seeders only under its seed contract, the `SEED_LAYOUT` its incarnation was issued under (D22). The handshake is versioned (`v: 1`, required; anything else is malformed) and carries the features a client implements; a root's `lexical-y-require:<feature>` keys are requirements a session must meet (stale with material, else refused), and the five verdicts are permanent, with an optional diagnostic `reason`. The mechanism ships with the migration entries; raising `MIN_LAYOUT` above 1 is the layout 3 change's. | Every collaborative system that migrates safely has one writer and refuses old sessions (tldraw, Linear, Replicache, Figma); a client that migrates on open races the server. An epoch in a client's state vector does not prove its pending edits are new, a fresh document with the same root accepts old updates, and a room recreated under the same name admits an old copy (each reproduced in review), so the fence is a generation tracked outside the Yjs document. Frozen steps keep each layout change in its own module, outside the core, so a migration is reproducible and reviewable on its own; the core keeps reading every layout from `MIN_LAYOUT` up and forgets one only when a release raises the floor (D110), whose rooms the published steps still migrate. Replaces the "no server-side update filter" clause of D09 for authorities that migrate. | `DECIDED` | 11-03 | [y.md: Changing the layout and migrating][y-layout], [y-server.md: Migrating stored documents][y-server-migrate] |
| D109 | **The Yjs encoding under the binding's root is private: direct writes are unsupported.** The root, its record keys (`lexical-y:<n>`, `lexical-y-schema:<n>`, `lexical-y-epoch`, `lexical-y-require:<feature>`, any `lexical-y-*` attribute) and every node, marker, format and state key below it belong to the binding. Apps, agents and tools change a document through the editor, `editYState` or a migration step. In development builds the binding reports a local transaction of another origin (not its own, not a `Y.UndoManager`'s, not a migration's) that changes the content under its root with `RAW_YJS_WRITE_WARNING` (root, what changed first, the origin's constructor name), once per binding and origin: a diagnostic judged by origin and locality, from a binding that has read its document (not while it is pending), skipping any transaction the binding also wrote in (an editor edit or binding undo inside an app's `doc.transact` joins it): it may miss a raw write, never report the binding's own. Production builds carry no check. | A raw write skips every invariant the binding keeps (layout and schema records, markers, run ends, recovery), so it can leave a document other clients read differently. It is a programmer mistake, so it is reported where programmers look (a development warning) and never thrown in production. The README's wire format documents the encoding for readers. | `DECIDED` | 11-04 | [y.md: Wire format][y-wire] |
| D110 | **Old layouts while experimental: a release may stop reading one; adding a layout never moves a room.** While `@lexical/y` is experimental, a release may raise `MIN_LAYOUT` and stop reading an older layout, as layout 3's release did for layouts 1 and 2. Rooms stored in it then open read only until their server migrates them with the published steps, and the release raises `SEED_LAYOUT` with the floor (servers issue new incarnations for never-seeded rooms, the seed contract of D22); such a release says so in its release notes and changelog, and apps that store rooms plan a server-side migration for it. No text is lost. | `ACCEPTED LIMIT` | 11-06 | [#9835], [limits] |
