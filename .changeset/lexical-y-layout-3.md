'@lexical/y': minor
---

[breaking] Store format runs as paired runs (layout 3), and read and write layout 3 only: `MIN_LAYOUT`, `LAYOUT_VERSION` and `SEED_LAYOUT` are now 3

Each run of a text format, link, text field, text node type or comment id is now an opener and an end that names it, so concurrent formats of one key nest instead of cutting each other short, and a format's undo removes exactly its own run. Rooms stored at layout 1 or 2 open read only, showing their content, until they are migrated with `@lexical/y/migrate/2to3`, which keeps every character, node and line marker with its Yjs id and reads the same before and after. Older `@lexical/y` releases open a layout 3 room read only (`UNSUPPORTED_LAYOUT_WARNING`, reason `'newer'`). Raw Yjs writes under the root are unsupported (development builds report them with `RAW_YJS_WRITE_WARNING`): code that writes formats straight into Yjs (`Y.Node#format`) anyway still converges, but in a layout 3 room its plain items can change other text's formatting; write through an editor or `editYState` instead. An array it stores under one of those names, other than layout 3's own end shapes, is never shown as a value and is kept as stored: those shapes are reserved for ends that a later layout may add. Any other value it stores there, an object keyed by array indices or a typed array included, reads as that value. A text class's shown format must depend only on its class, fields and NodeState, not on its text content or length, its editor, or where it is attached. The binding's initialization and follow-up transactions now use instances of a class of their own as their origin, so an app `UndoManager` that tracks `Object` origins no longer captures them.

Migration: upgrade every client of a room together. A server migrates each stored room when it loads it, before serving it, with `prepareYRoom` (`@lexical/y/server`) or `migrateYState` (`@lexical/y/migrate`), whose default steps now include `@lexical/y/migrate/2to3` (a step list of your own adds it after `@lexical/y/migrate/1to2`); keep the generation fence (`checkYSession`) on every relay, so clients still on an older release never receive a migrated room, and replace the incarnation of rooms not yet seeded (`needsNewIncarnation(room, SEED_LAYOUT)`), since the seed layout changed. Clear an app `UndoManager` at the migration with `onYMigrationEpoch(doc, fn, root?)`; one that is not cleared can restore formatting the migration replaced.

Detect: rooms whose root records `lexical-y:1` or `lexical-y:2` but not `lexical-y:3`; `UNSUPPORTED_LAYOUT_WARNING` with `reason: 'older'`; server step lists of your own without `@lexical/y/migrate/2to3`; code that calls `format()` or inserts with attributes on the `lexical-y` root's text.

Verify: open a stored layout 2 room after migrating it on the server: it is editable and reads as before; without the migration it opens read only and nothing is written.

Layout 4, in the same release, raises the floor again (see its entry): a room at layout 3 then migrates with `@lexical/y/migrate/3to4` too.
